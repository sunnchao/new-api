# 待生效订阅激活与 Web 管理能力设计

## 背景

`model/subscription_scheduled.go` 仍承担续费订阅的核心状态机职责：创建待生效订阅、用户或管理员手动激活，以及定时激活到期记录。该文件不能删除，也不能用旧的“直接延长当前订阅”逻辑替代。

当前合并后的主要阻断是 `ActivateScheduledSubscriptionTx` 仍调用已经删除的 `UpdateUserGroupCache`，导致 `model` 包无法编译。旧方法不能直接恢复，因为它不符合当前基于 `auth_version` 的认证缓存刷新机制；在数据库事务内直接调用 `RefreshUserGroupCache` 也不正确，因为该方法通过全局数据库连接读取数据，可能在事务提交前读到旧用户组。

Web 用户侧已经可以展示并手动激活待生效订阅，但管理员订阅表尚未完整支持 `scheduled` 状态，已有管理员激活 API 也没有调用者。

## 目标

- 恢复待生效订阅激活代码的可编译和可运行状态。
- 保持用户、管理员和定时任务三个激活入口的一致事务语义。
- 在事务成功提交后刷新用户组认证缓存。
- 保留用户确认的业务规则：提前激活新订阅时，旧订阅继续有效，允许两份订阅并行生效。
- 补齐 Web 管理端对待生效订阅的展示、筛选和立即激活能力。
- 修正前端续费文案，使其与“创建新的待生效订阅”的实际行为一致。
- 清理无调用且语义已经过时的直接续费实现。

## 非目标

- 不删除或合并 `subscription_scheduled.go`。
- 不重构完整的订阅 service 层或重新设计全部订阅状态机。
- 不改变现有数据库结构、HTTP 路由或响应包络。
- 不在提前激活时结束、缩短或退款旧订阅。
- 不改变消费链路只读取 `active` 订阅的规则。
- 不解决与本功能无关的前端合并遗留类型或 lint 错误。

## 方案选择

采用“保留 scheduled 状态机，修复事务与缓存边界，并补齐管理端”的方案。

没有选择将代码并入 `subscription.go`，因为这只会扩大文件职责和合并冲突范围，并不减少业务复杂度。也不在本次抽象完整的订阅状态机服务，因为这会改变大量调用关系和事务边界，超出恢复缺失功能所需范围。

## 后端设计

### 激活事务结果

`ActivateScheduledSubscriptionTx` 继续负责一次待生效订阅的数据库状态转换，但不再直接操作缓存。它返回一个明确的内部结果，表达：

- 订阅是否实际从 `scheduled` 转为 `active`；
- 需要处理的用户 ID；
- 激活过程中用户组是否实际发生变化。

用户激活、管理员激活和定时激活入口均根据该结果决定是否计数以及是否在提交后刷新缓存。调用方不通过 `UpgradeGroup` 字段猜测用户组是否变化。

### 数据库事务

激活流程在事务内完成以下操作：

1. 使用 `lockForUpdate(tx)` 锁定目标订阅。该帮助函数在 MySQL/PostgreSQL 上发出行锁，在不支持 `FOR UPDATE` 的 SQLite 上跳过锁语句。
2. 再次确认目标记录仍为 `scheduled`。用户入口还必须验证订阅所有权。
3. 根据激活时间计算相对原 `StartTime` 的偏移量。
4. 等量平移开始时间、结束时间，以及普通、小时、日、周、月额度的所有非零重置时间。
5. 将订阅状态改为 `active`。
6. 仅在 `UpgradeGroup` 非空且与用户当前分组不同时，保存 `PrevUserGroup` 并更新用户分组。
7. 保存订阅记录并提交事务。

提前激活使用当前时间，旧订阅保持原状态和原周期。定时激活使用订阅原定 `StartTime` 作为激活时间，避免任务调度延迟缩短订阅周期。

### 提交后缓存刷新

只有事务提交成功且用户组实际变化时，调用方才调用现有 `refreshSubscriptionUserGroupCache(userId, operation)`。该方法从已提交数据重新读取用户组，并走当前认证缓存和 `auth_version` 机制。

缓存刷新失败不撤销已经提交的订阅激活。数据库保持事实来源，刷新帮助函数记录包含用户 ID 和操作来源的系统错误，便于排查。事务失败或记录被其他请求抢先处理时不刷新缓存。

三个入口使用可区分的操作来源：用户立即激活、管理员立即激活、定时自动激活。

### 并发和批处理

手动重复点击或多个服务实例同时处理同一记录时，只有成功锁定并完成状态转换的事务返回“实际激活”。后续请求将目标视为不存在或已非待生效状态，不重复平移时间、修改用户组或刷新缓存。

`ActivateDueScheduledSubscriptions` 只对实际完成转换的记录增加返回计数。查询后被另一个实例抢先激活的记录不计数，从而保证批处理循环的终止判断与真实处理量一致。

### 旧实现清理

删除 `model/subscription_renew.go` 中无调用的 `renewUserSubscriptionTx`。该函数直接延长和累加当前订阅，与当前“创建独立 scheduled 快照”的续费规则不等价，继续保留会造成未来误用风险。

`EnsureNoExistingScheduledRenewal`、`CreateScheduledSubscriptionTx` 和现有续费支付完成链路保持不变。本次不扩大到支付流程或数据库唯一约束调整。

## Web 设计

### 用户钱包

保留现有待生效订阅卡片和激活 API，只完善行为一致性：

- 继续展示待生效数量、`scheduled` 状态、预计生效时间和“立即生效”按钮。
- 确认弹窗明确说明立即激活不会结束当前有效订阅，两份订阅可能同时生效。
- 请求期间禁用激活操作，避免用户连续提交。
- 成功后并行调用 `fetchSelfSubscription()` 和页面已有的 `onPurchaseSuccess` 用户资料刷新回调，不做仅更新本地状态的乐观处理。
- 失败时保留当前数据，并优先展示后端返回的错误信息。

### 管理员订阅表

在 `all-subscriptions-table.tsx` 中补齐：

- `STATUS_CONFIG` 和状态标签映射增加 `scheduled`。
- 状态筛选增加“待生效”。
- 只有 `scheduled` 记录显示可用的“立即激活”操作，并调用已有 `adminActivateScheduledSubscription`。
- 确认弹窗说明激活不会终止用户当前有效订阅。
- 成功后失效 `admin-all-subscriptions` 查询并重新获取表格数据。
- 失败时保留当前行状态并显示错误消息。
- 已激活、已过期、已取消或已删除的记录不提供立即激活操作。

管理员手动续费的确认文案由“延长当前订阅”改为“按原套餐创建新的待生效续费订阅”，以匹配后端实际行为和返回结果。

### 类型与国际化

为当前前后端已经使用的状态定义共享联合类型：`active | scheduled | expired | cancelled | exhausted`。用户订阅 Zod schema、用户订阅记录和管理员订阅概览共用该类型，不继续使用宽泛的 `status: string`。

本功能新增或修改的用户可见文案放入 subscriptions 功能模块的 `i18n.ts` 资源并通过 `useTranslation()` 使用。钱包侧若已有等价功能本地文案则复用，不将功能专属文本加入全局 locale 文件。

## 错误处理

- 参数无效、记录不存在、用户越权或状态已变化时不产生数据库修改。
- 数据库读取或保存失败时回滚整个激活事务。
- 数据库成功提交而缓存刷新失败时记录错误，不返回伪造的事务失败，也不反向撤销激活。
- 前端只在 API 明确成功后关闭确认流程并刷新列表；业务失败优先显示响应消息，网络异常显示通用激活失败提示。
- API 路由、权限中间件和响应包络保持兼容。

## 测试设计

### 后端

新增或调整确定性的回归测试，验证以下用户可见和跨模块契约：

- 创建待生效订阅时正确快照套餐数据，且消费查询不会把它视为有效订阅。
- 提前激活后旧订阅仍为 `active`，新订阅立即变为 `active`。
- 新订阅总时长不变，所有非零重置时间与开始时间等量平移，零值保持为零。
- 定时激活使用原计划锚点，而不是定时任务实际执行时间。
- 用户组发生变化时保存前一分组，并在事务提交后触发刷新；分组相同时不触发无意义刷新。
- 用户不能激活其他用户的记录，管理员可以激活任意待生效记录。
- 重复激活和多处理器竞争不会重复更新，批处理只统计实际激活数量。
- 事务保存失败时用户分组和订阅状态一起回滚。
- SQLite 测试不生成不支持的 `FOR UPDATE`，生产查询统一通过 `lockForUpdate(tx)` 保持三种数据库兼容性。

新编写的 Go 测试使用 `testify/require` 处理前置条件和致命断言，使用 `testify/assert` 检查非致命结果。

### 前端

在现有前端测试基础设施中增加定向测试，验证：

- `scheduled` 状态标签和筛选选项可见。
- 立即激活操作只对待生效记录可用。
- 用户和管理员确认文案说明并行生效规则。
- 管理员操作调用正确 API，成功后刷新查询，失败后保留当前行。
- 续费确认文案描述创建待生效订阅，而不是延长当前记录。
- 订阅状态联合类型覆盖后端实际返回值。

测试避免断言组件私有实现或文件布局，优先验证用户可见行为和 API 交互契约。

实施完成后执行：

```bash
go test ./model ./service/...
go test ./controller/... ./router/...
go build ./...
```

前端从 `web/` 目录使用 Bun 执行相关测试、类型检查和生产构建。具体命令以当前 `package.json` 已定义脚本为准。

若全量前端检查仍存在合并前已有错误，记录完整命令结果，并将本次修改引入的问题与可复现的存量问题分开报告。本功能涉及的文件不得留下新增类型、lint 或测试错误。

## 验收标准

- `model` 包不再引用缺失的 `UpdateUserGroupCache`，后端可编译。
- 三种激活入口均在事务提交后按需刷新用户组认证缓存。
- 手动提前激活不会改变旧订阅状态或结束时间。
- 定时任务不会因并发抢占虚增激活数量。
- 所有待生效订阅行锁使用 `lockForUpdate(tx)`。
- 用户钱包明确告知并行生效行为并能成功刷新激活结果。
- 管理员可以查看、筛选并立即激活 `scheduled` 订阅。
- 管理员续费文案与创建待生效订阅的真实行为一致。
- 后端回归测试、前端定向测试和相关构建检查通过，或明确区分与本次无关的存量失败。
